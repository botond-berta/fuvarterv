# Fuvarterv — the Java compute service

The scheduling domain, ported from `src/domain/` (JavaScript) to Java 21. Why this exists,
what it costs and what it replaces is [ADR-29](../docs/DECISIONS.md#adr-29--the-scheduling-domain-moves-to-a-java-service-the-browser-ui-stays);
the staging is [`ACTION_PLAN.md` §6](../docs/ACTION_PLAN.md#6-p3--the-java-compute-service-adr-29).
This file says **only what is true today**.

Nothing here is wired to anything. There is no Spring, no HTTP, no database: the port had to
be verifiable on its own before an HTTP layer existed to hide behind. The JavaScript domain is
still what the app runs, and it stays that way until P3-5 deletes it in one commit.

```
mvn -f server/pom.xml test     # the parity suite
npm run parity:fixtures        # regenerate the fixtures from the JavaScript
```

## The governing rule

**The JavaScript implementation is the specification.** It is the one that has been right in
production for a season. The port is correct when it reproduces the JavaScript's output
exactly — not when it looks like better Java.

So: a red parity test means the port is wrong. **Do not regenerate the fixtures to make a test
pass.** That deletes the only evidence of what the behaviour used to be, and there is no second
copy.

## What is verified, and what is merely ported

The fixtures are generated by `tools/parity/gen-fixtures.js`, which runs the JavaScript domain
over 56 states across 14 scenarios and records what it returned. `ParityTest` replays every one
through the Java and compares structurally.

**Verified directly** — its own fixture and its own assertion:

`legMin`, `matrixKey`, `allPoints`, `baseOf`, `venueNeedsVignette`, `weekOccurrences`, `legPax`,
`bestStationOrder`, `legRouteOrder`, `planOda`, `planVissza`, `splitStationsByCapacity`,
`driverAvailableFor`, `mergeShifts`, `spanOf`, `driverPay`, `onSiteWait`, `genDayTasks`,
`resolveDay`, `dayStats`, `optimizeDay`, `ridesFromChains`.

**Verified indirectly** — no fixture of their own, but `optimizeDay` and `resolveDay` parity
cannot hold unless these are right: `mkChain`, `minCostChains`, `chainFrom`, `chainTo`,
`chainUse`, `resourceClash`, `assignResources`, `contentionReasons`, `venueDepartMin`.

**Ported but NOT covered by any fixture.** These are transcribed and compile, and nothing proves
them. Treat them as unreviewed until P3-3 gives them a test:

`normalizePlate`, `plateExists`, `findRides`, `rideWindow`, `occursOnSameDay`, `findConflicts`,
`seatSum`, `chainRefs`, `deleteGuard`, `rideBelongsToDay`, `teamRouteOrder`, `teamPax`,
`teamLeg`, `hasOwnStops`.

**Deliberately not ported:**

| What | Why |
|---|---|
| `computeMatrix` | Makes a network call. It is the swap point for a self-hosted or paid router (R2), so it belongs with the HTTP layer, not here. |
| `withGeneratedRides` | Rewrites `state.rides`. A write to the blob belongs to P3-3, where the state is a raw `JsonNode`. Its two halves (`ridesFromChains`, `rideBelongsToDay`) are here. |
| `defaultMapCenter`, `r5`, `CLUB_CENTER` | Serve the map widget. ADR-29 draws the line at what prices, times or schedules. |
| `fmtDate`, `fmtDateFull`, `fmtWeekRange` | Presentation, and Hungarian. Same line. |
| the form validators, as the app's first line | They stay in JavaScript for the keystroke feedback. The copies here are the rule; the client's are a convenience. |

`DAYS` is the one piece of UI copy that had to come along: the explanation strings index it by
weekday number, and those strings are compared literally.

## The harness has teeth

A green suite proves nothing unless it can go red, so each trap named in P3-2 was introduced
deliberately and the suite was re-run:

| Mutation | Failures |
|---|---|
| Treat an empty headcount as an explicit zero (ADR-23) | 14 |
| Reassociate the wage arithmetic to `p * (wage / 60)` | 23 |
| A plain `HashMap` for the locked-chain grouping and the per-driver totals | 1 |
| Reverse a return leg that has its own stop list (I2) | 28 |

The third one is the cautionary tale. On the first 48-fixture set it produced **zero** failures:
the trap is real but nothing generated enough locked chains for iteration order to be
observable. The `multi-locked` scenarios exist for that reason, and their chain ids are
deliberately inserted out of sort order. A trap you cannot demonstrate is a trap you have not
tested.

## What the port found

Locked tasks are not re-checked against capacity, availability or the vignette. Fixture
`45-everything-1` puts an eleven-person task on an eight-seat bus and keeps it there, and the
Java reproduced that exactly — which is how we know it is the JavaScript's behaviour and not a
port bug.

It is defensible: a lock is the user's explicit instruction, and `resolveDay` does attach a
visible issue, so ADR-24 holds. But the property test in `test/optimizer.test.js` asserts
capacity over *every* chain in the proposal, and it only passes because it never generates a
saved schedule. The claim in that comment is wider than the guarantee in the code.

Nothing was changed in the JavaScript over it. `ParityTest.lockedChainsAreNotReCheckedButAreReported`
pins the behaviour instead: the chain must be kept **and** the issue must be reported. If a
future optimizer quietly fixes these, or quietly stops explaining them, that test goes red.

## Notes for whoever continues

- **Every number is a `double`.** JavaScript has no other kind. Introducing an `int` anywhere in
  the cost or timetable path risks integer division the original cannot do.
- **`Js` is the only place that knows JavaScript coercion rules.** `Number(x) || 0`, truthiness,
  `?? `, `toFixed`, `Math.round`, and how a value renders inside a template literal. Do not
  reimplement any of it inline.
- **`LinkedHashMap` and `LinkedHashSet`, never the plain ones.** See the table above for what
  happens otherwise, and how nearly it went unnoticed.
- **`Geo.haversineKm` associates its arithmetic oddly on purpose.** `Math.toRadians` computes
  `x * (PI / 180)` where the original computes `(x * PI) / 180`. They differ in the last bit,
  and that bit survives into a rounded minute.
- **`optimizeDay` is not reproducible field for field**, because skeleton chain ids come from
  `uid()`, which is `Math.random()`. The fixtures blank them on both sides; `Ids` is the seam
  that makes them deterministic in a test.
